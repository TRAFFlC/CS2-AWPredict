# CS2-AWPredict

**CS2 赛前预测：胜方 · 选图 · 比分 · MVP**

> Alpha 1.1.1 · 基于 Valve 排名（VRS）与 ban/pick 顺序的**赛果**预测。
> 非选手层 / 枪械层预测（不预测击杀、命中率、AWP 数据）。

一个用真实赛事结果反复校准过的 CS2 赛果预测器。它最有价值的部分不是预测数字，
而是**知道自己什么时候不该被相信**——下面所有「已知的不可信」都写在明处。

## 快速开始

```bash
git clone <this-repo>
cd CS2-AWPredict

# 命令行
python -X utf8 predict.py G2 FURIA 3

# Web 界面（推荐：选队 + 点预测）
python -X utf8 predict_gui.py --open      # → http://127.0.0.1:8765/
```

无第三方依赖，Python ≥ 3.10 即可（前端为原生 HTML/JS）。仅每日自动抓取 VRS
需要可选的 Playwright 与系统 Chrome。

### 每日自动更新 VRS 排名

`fetch_vrs.py` 用 Playwright 驱动系统 Chrome 无头打开 HLTV 的 Valve 全球排名页，
直接从 `div.ranking` 的 DOM 读取队伍，再复用 `ingest_vrs.py` 的校验与去重逻辑生成
`data/vrs_rank_<日期>.json`。**当天快照已存在时直接跳过，不发起任何网络请求**；
页面日期还没更新时也不会覆盖旧快照，因此可以安全地重复运行。

```bash
python -X utf8 fetch_vrs.py                  # 抓本机今天；已有快照则跳过
python -X utf8 fetch_vrs.py --date 2026-10-26
python -X utf8 fetch_vrs.py --dry-run        # 只抓取/校验，不落盘
python -X utf8 fetch_vrs.py --force          # 已有同日快照也重抓
```

依赖：`pip install playwright`，并使用系统安装的 Chrome（不需要
`python -m playwright install chromium`；脚本以 `channel="chrome"` 启动）。
不要改回 `requests` / `curl`：HLTV 前面的 Cloudflare 会返回 403。

本机已注册每日计划任务（每天 13:00；错过则在下次可用时补跑）：

```powershell
Get-ScheduledTask -TaskName "CS2-AWPredict-update-vrs"
Start-ScheduledTask -TaskName "CS2-AWPredict-update-vrs"   # 立即跑一次
.\update_vrs.bat                                            # 手动入口
```

计划任务通过 `wscript.exe //B update_vrs_hidden.vbs` 无窗口运行；日志在
`data/cache/update_vrs.log`，结构化运行记录在 `data/cache/fetch_vrs_runs.jsonl`。
改时间：`Set-ScheduledTask -TaskName "CS2-AWPredict-update-vrs" -Trigger (New-ScheduledTaskTrigger -Daily -At 14:00)`。

> **Windows 开机自启**：计划任务 `issue014-predict-gui` 应调用本仓库的
> `start_predict_gui.bat`。历史坑：任务曾指向旧开发副本 `014-scratch`，
> 该副本只有旧快照，导致「更新 rank 后一重启就回到旧榜」。旧副本的启动器
> 现已改为跳转本仓库；重建计划任务时不要指回它。

## v1.1.1 变更

本版全部是**「显示与口径」层的修复**，不改任何预测逻辑的参数。四个缺陷的
共同点是：**系统算对了，但呈现或度量把它毁了，而使用者只看到呈现。**

### 1. 选图显示把模型的排名扔了（用户可见）

`VM.predict_set` 返回的是**按概率排好序**的列表，但三处立刻
`tuple(sorted(...))` 按字母重排。屏幕上是 `Dust2 / Mirage / Nuke`，
而概率是 `Mirage 74% · Nuke 65% · Dust2 57%`
——**第一位是概率第三的图**，看着像首选小镇。

字母序原本是为「计划身份」服务的（`_plans()` 去重要比 tuple），
而 `scorer.py` 默认 `maps_order_matters=False`、**按集合判分、完全不看顺序**，
所以这个排序对计分毫无用处。

修法：`plan["maps"]` 保持字母规范序（计分身份），**新增
`plan["maps_ranked"]` 专供显示**；前端按概率降序渲染且每张图自带概率，
池内未选单列一行。

> ⚠ 该 bug 有**三份副本**（CLI / 内联模板 / `predict_page.html`），
> 且 `predict_gui.py` 优先加载外部 `predict_page.html` —— 改内联模板
> **完全不生效**。本版加了 `check_display_paths.py` 守卫，
> 它扫描 `.py/.html/.js`、并校验两份模板同步；
> 该守卫另有 `_t_inject.py` **注入验证**（把 bug 注回源码、确认守卫真的 FAIL），
> 因为第一版守卫的正则从未匹配过任何东西、一直假通过。

### 2. `draft` 形状与小图池不兼容（结构缺陷）

`simulate_veto` 对 `bo>=5` 一律排 8 个动作（2 ban + 4 pick + 2 ban），
而标准 CS2 bo5 图池 ≥9 张。**小图池赛事喂不满**：

```
池 = 7、bo5  ⇒  模拟只出 4 张（少 1 张）
```

真实 7 图 bo5 的 `veto_order` 是 `4 pick + 1 decider`、零 ban。
选图按**集合**判分、大小须等于 bo ⇒ 那一格白丢。

修法（`simulate_veto(..., adaptive=True)`，**本版默认**）：
`ban 数 = clamp(len(pool) - bo, 0, 标准上限)`，保证 `len(picks) == bo` 恒成立。
`adaptive=False` 保留旧行为供 A/B。

配对检验（同模型、同样本、同评估器）：

```
valid  426 → 428   Δ=+0.008/场  p=0.815
test   553 → 550   Δ=−0.009/场  p=0.751
bo5（缺陷真正发作处）Δ=0.000，有效样本仅 6 场
```

**零可测收益。** 上线理由不是收益，而是旧行为返回**大小错误的集合**
是确定性错误，而修它的实测代价为零。

> ⚠ 代价：ban 步数压到用满图池后，两种先手顺序**常收敛到同一集合**（只差顺序）。
> 旧行为把 leftover 也并进集合，才让集合「看起来」不同——那是假差异。
> 后果：小图池下 `sim_features` 丢失先手信息（权重只会 0/1）。
> 这是真实赛制后果，**不是 bug，不要「修」**。

### 3. 真值为空的场次污染评测分母（度量口径）

`truth_maps_B.jsonl` 里 **bo=25 的 4 场**（EWC 2026-08-12）真值图集是空的
（`maps: []`、`suspicious: true`、notes 写「未知 bo=25，无法判定应有图数」），
而 `evaluate()` 对空真值**零过滤** ⇒ 每场白送 5 个**必然 miss** 的槽位进分母。

**数据缺失被当成了反例**。修法：`is_scorable()` + `evaluate(..., skip_unscorable=True)`
（**本版默认 True**）。只动分母，不动任何预测、不动 C 的选取。

```
test 选图命中率  61.38% → 62.77%（+1.39pp）
```

连带修了 `evaluate_rank`（对照臂）——否则 `full_model` 走新口径、
对照臂走旧口径，两条百分比**并排打印却不同分母**。

### 4. 「分数优先 / 排名优先」一直是混着的

`predict.py::predict_from_sample` 里 **无论 `--objective` 是什么，
都会无条件用 `rank_pick` 覆盖胜方**。后果不是「不优雅」，是**实验失真**：
此前 A/B 报的「胜方分歧 0/559」是**假象**——两臂胜方都被 rank 锁死了，
本来就不会分歧；被测到的只有计划排序，**胜方差异根本没进实验**。

修法：拆成**两个正交开关**：

```
--objective score|rank   计划排序（比分/MVP/选图怎么排）
--winner   model|rank    胜方来源（谁说了算）
```

- 纯分数优先 = `--objective score --winner model`（**第一次真正可达**）
- 排名优先   = `--objective rank  --winner rank`
- `winner_policy` 默认 `rank` ⇒ **生产行为不变**（保留既有定案）

拆开后重测的真实分歧率：

```
valid  53/242 = 21.9%    模型 64.0% vs rank 59.5%   McNemar p=0.169
test   86/317 = 27.1%    模型 67.2% vs rank 64.7%   McNemar p=0.451
```

> ⚠ 这**不能**推翻「遵循 rank」的定案：那次是**时间前进式、无泄漏**设计，
> 本次是冻结模型跑全桶，**方法不同、不可比**；且 p=0.169/0.451
> **两个方向都不显著** ⇒ 默认不动。真正该做的实验是
> **把两轴拆开重跑时间前进式**（`exp_winner_axis.py` 已把两轴拆开，
> 但它是冻结模型口径）。

## 三个「知道自己不可信」的地方

### 1. 胜方为什么不听模型的

模型 Elo 在 110 场上是 63.6%，rank 热门 **74.5%**，落后 11.8pp，
McNemar p=0.0192 —— **这次是真的显著**，不是擦边。

而且**没有任何一个分层里模型能翻盘**（rank 名次差分 6 桶，全是 rank 赢）：

```
名次差桶      场次   rank命中   模型命中    差(pp)
[ 0,  2]       13     61.5%     30.8%    -30.8
[ 3,  5]       17     64.7%     52.9%    -11.8
[ 6,  9]       12     83.3%     75.0%     -8.3
[10, 15]       20     55.0%     50.0%     -5.0
[16, 25]       18     83.3%     77.8%     -5.6
[26, 99]       30     90.0%     76.7%    -13.3
```

实力最接近的桶（名次差 ≤2）差距**最大**，不是最小 —— rank 在"看起来该拼运气"
的场次里反而最可靠，因为此时 Elo 差也最小、几乎无信息。

按月分层（同样 out-of-sample）：

```
月份        场次    rank      模型
2026-09       70    64.3%     64.3%
2026-10       40    62.5%     60.0%
```

按 rank 差分层：

```
[0.50,0.60)   44 场  模型 56.8%
[0.60,0.70)   42 场  模型 71.4%
[0.70,0.80)   21 场  模型 57.1%
[0.80,0.90)    3 场  模型 100.0%
```

### 1b. 融合策略（模型置信度高跟模型、低跟 rank）—— 已证伪

扫阈值 t：`conf ≥ t` 跟模型，否则跟 rank。

```
   t   跟模型场数   融合命中   vs 纯rank   McNemar p
 0.50     110       62.7%     -11.8pp     0.019
 0.54      95       67.3%      -7.3pp     0.134
 0.58      71       71.8%      -2.7pp     0.549   ← 全表最优
 0.62      61       72.7%      -1.8pp     0.727
 0.66      39       73.6%      -0.9pp     1.000
 ≥0.74     ≤13      74.5%      ±0.0pp     1.000
```

**任何阈值都没跑赢纯 rank。** 最好的一档也差 2.7pp；t ≥ 0.74 后完全退化成纯 rank。

### 1c. 模型置信度与它的实际优势**反向**

```
置信度区间        场次   rank命中   模型命中    差(pp)
[0.50,0.55)         21     85.7%     52.4%    -33.3
[0.55,0.60)         21     81.0%     61.9%    -19.0
[0.60,0.65)         27     66.7%     66.7%     +0.0
[0.65,0.70)         19     68.4%     63.2%     -5.3
[0.70,0.80)         19     68.4%     63.2%     -5.3
[0.80,0.90)          3    100%     100.0%     +0.0
```

模型**越没把握的时候，rank 领先越多**（低置信档差 33pp）。所以模型置信度
**不能**当作"何时该信模型"的门控信号——它和模型的实际优势方向相反。

这也解释了 1b 为什么必然失败：融合规则里"低置信→跟 rank"这半边方向是对的，
所以它最多把结果拉回接近纯 rank，永远超不过；"高置信→跟模型"那半边是错的，
在 0.60–0.80 这个最宽的置信带里净贡献为负。

**结论：胜方项就按 rank 走，不要接模型，也不要接置信度。**
模型的价值在选图、比分、MVP 三项上，不在胜方。

### 2. 换更新的排名 ≠ 更准

同样是**无泄漏**口径，69 场上对比两个排名体系：

```
csapi / VRS  2026-09-05    50/69 = 72.5%    ← 当前使用
HLTV         2026-09-07    43/69 = 62.3%    ← 本地有一份更新的快照，反而低 10.2pp
HLTV         2026-10-05    51/69 = 73.9%    ← ⚠ 前视偏差，不可用
```

最后一行是最容易自欺的一种错误：**用 10-05 的排名去评 9 月的比赛**，
该快照已经吃进了被评比赛的赛果，数字会虚高。

结论：差距来自**排名体系不同**，不是「数据旧」。所以刷新现有体系的快照有价值，
**换源不是解法**。

### 3. MVP 在冷门队上基本是随机

候选池是胜方 5 名选手（随机基线 0.20）。真实命中率**按选手历史出场数分档**：

```
选手历史 ≥18 场：真实命中 0.39 ~ 0.41
选手历史 <18 场：真实命中 0.12 ~ 0.15  ≈ 随机
```

冷门队几乎总落在低丰度档。**别把那里的概率当成把握程度**；Web 界面只在
**完全没有阵容数据**时红字提示「MVP 项只能取随机」，不再对 `<18` 场逐队告警
（大多数队伍样本都不足，逐队提示没有区分度）。

## 数据可信度：`maps_verified` 闸门

v1.0.1 起，增量赛果记录带两个溯源字段：

```jsonc
"maps_full_B":  ["Ancient", "Anubis"],   // 实际打过的图（2:0 就是 2 张，不塞未打的决胜图）
"maps_verified": true,                    // 图序是否经过权威确认
"maps_evidence": "per_map_scores",        // 判定依据
```

`maps_evidence` 的取值与含义：

| 值 | 含义 |
|---|---|
| `per_map_scores` | 带真实逐图比分 ⇒ **比分顺序即图序，天然自证** |
| `user_bp` | 图序可在主理人原话里逐字命中 |
| `fissure_results_maps` | 与 `fissure_*_results.json` 的 `maps` 字段一致 |
| `user_confirmed` / `user_per_map_*` / `user_pool_*` | 主理人直接指定 |
| `inferred` | 无上述证据，**不参与选图训练** |

`maps_verified=false` 的记录**会被 `state_snapshot.ingest()` 拦在选图模型之外**
（只更新胜负/比分/图池统计），避免脚本推断的图序污染 ban/pick 模型。

**为什么要加这个字段：** `maps_full_B` 原本是自由列表，
`Ancient / Anubis / Dust2` 任意排列都能通过校验，导致图序记错长期无人发现。
加标记后，"猜的"与"核实过的"不再长得一样，`grep '"maps_verified": false'` 一眼可查。

当前 110 条记录**全部 `true`**（2026-10-14 主理人逐场核对）。

## 已证伪的路（省得你重走）

| 尝试 | 结果 |
|---|---|
| 全局概率校准（Platt / isotonic） | 在 test 与真实赛事上均**变差**，不挂校准器 |
| 概率融合 rank + 模型 | 69.8% / 62.8% 都好于融合的 60.5%（错误相关，平均只加噪） |
| **置信度门控（高置信跟模型 / 低置信跟 rank）** | **110 场上扫遍 t∈[0.50,0.92]，无一档超过纯 rank；最优 t=0.58 仍差 2.7pp** |
| **用模型置信度当"何时该信模型"的信号** | **方向是反的：置信度越低，rank 领先越多（低置信档 −33.3pp）** |
| 比分：恒报 2:1 / 阈值改报次高 | 四种改法**全部**更差 |
| 选图：T4 专项调参 | 选图已达**自身概率上界**，解码层 100% 取满 |
| 去掉队伍级特征 | 高低丰度段**双双下降约 4pp** |
| NNUE 改架构 | 一次架构偏离 + 一次诚实的负结果 |
| MVP 按 bo1/bo3/bo5 分档 | 真正的分档变量是**丰度**，不是赛制 |

这些负结果的价值高于结论本身：它们共同说明**三项的瓶颈是信息量，不是调参**。

```
fetch_vrs.py          HLTV → data/vrs_rank_<日期>.json（Playwright + 系统 Chrome）
update_vrs.bat        每日抓取入口（计划任务 / 手动）
update_vrs_hidden.vbs 计划任务的无窗口启动器
data/                 语料、VRS 排名、精简排名档案、增量快照
  cache/              抓取缓存、锁、运行日志（不入库）
  groundtruth/        各赛事真实赛果
  rankings/           精简排名档案（0.7MB，由上游 103MB 派生）
experiments/          实验脚本（上限诊断、标定、复测、回放）
```

**为什么是平铺的**（模块与数据分区，但不在 `src/` 下）：运行时代码大量使用
`os.path.join(HERE, ...)`，搬进包结构需改十余处路径解析。Alpha 阶段选择
「能跑 > 好看」，重构列为 beta TODO。

## 局限与已知问题

- **rank 快照会陈旧。** VRS 快照是某一时点的冻结值；本机虽有每日计划任务
  `CS2-AWPredict-update-vrs`，但它只负责「当天没有就抓一次」，HLTV 未更新或
  任务失败时仍会保持旧快照。界面会显示快照日期与陈旧天数，>30 天变黄、>60 天变红。
- **开机自启指向旧副本会静默回退旧 rank。** 常驻服务只读取自己工作目录下的
  `data/vrs_rank_*.json`；若计划任务启动的是 `014-scratch`，即使仓库里已有
  `2026-10-25`，页面也会显示该副本里最新的 `2026-10-19`。判断方法：看
  `/api/status` 的 `rank_snapshot` / `rank_teams`，以及仓库根目录
  `gui.launcher.log` 里的 `starting ... in <目录>`。
- **换 rank 快照不需要重启**（2026-10-19）：`python -X utf8 ingest_vrs.py` 落盘后，
  常驻服务在**下一个请求**时比对 `(mtime, size)` 指纹自动重建索引（毫秒级），
  页面 30 秒内自行刷新。但**账本快照**（`ingest_new.py --rebuild`）仍要 10~20 秒
  重建 Predictor，需要手点「刷新模型」或重启。
- **新榜未收录的队伍会退回旧榜兜底**，此时界面标橙色（下拉里名次带 `*`）——判定混了两个时间点。
- **bo5 的 2:0 不是最可能比分**：语料里 bo3 的 2:0 占 55.2%，bo5 的 3:0 只占 36.7%。
- **单场波动大**：以上百分比是几十场量级的估计，单场不要过度解读。
- 增量摄入的新记录若缺逐图比分/阵容，相关特征不会更新（会显式降级而非静默）。
